## 1. 설계 원칙

MemoLite의 목표는 **"메모장의 가벼움에 메모 관리를 더한 프로그램"** 이다. 아래 원칙은 두 페르소나에서 나왔고, 모든 단계의 판단 기준으로 쓴다.

| 원칙 | 근거 | 이렇게 한다 | 이렇게 하지 않는다 |
| --- | --- | --- | --- |
| **켜면 바로 쓴다** | 김민수: "잊어버리기 전에 메모해 두자" / 저니맵 "빠른 새 메모 진입" | 실행하면 커서가 빈 메모에 있다. 로그인, 설정, 시작 화면이 없다. | 첫 실행 마법사, 계정 |
| **저장을 신경 쓰지 않는다** | 이수진: "쉽고 안전하게" / N-004 데이터 손실 0건 | 쓰는 즉시 자동 보관된다. 삭제는 휴지통을 거친다. | "저장하시겠습니까?" 대화상자를 자주 띄우기 |
| **정리는 한 번, 고치기는 쉽게** | 김민수: "쌓인 메모를 한 번에 정리하자" / 저니맵 "분류 결과가 의도와 다를 수 있음" | 버튼 하나로 정리하고, 근거를 보여 주고, 되돌리기와 분류 변경을 바로 할 수 있다. | 결과 승인 단계, 복잡한 규칙 편집기 |
| **찾는 건 입력 한 번** | 김민수: "지난 회의 메모는 어디에 있지?" / F-008 | Ctrl+F로 입력하면 바로 결과가 나오고, 제목과 미리보기로 고른다. | 고급 검색 화면, 검색 옵션 대화상자 |
| **인터넷 없이, 설명 가능하게** | 이수진: 오프라인 / 제약: 외부 LLM 의존 배제 | 로컬 규칙으로 분류하고, 왜 그 주제인지 단어로 보여 준다. | 클라우드 API, 설명할 수 없는 분류 |
| **가볍게** | 제품 정의 / N-001 / N-006 | 기능은 작성, 정리, 조회, 검색에 한정한다. 데이터는 로컬 JSON 파일이다. | 협업, 동기화, 알림, 위젯 (PRD 범위 밖) |

## 3. 단계별 절차

각 단계는 **별도 브랜치와 PR**로 진행하고, PR을 머지하기 전에 `tests/Verify.ps1`과 CI가 통과해야 한다.

### 단계 0. 팀 결정 (11/25 ~ 11/26)

코드를 쓰기 전에 PRD v0.2에 확정해서 적는다.

- [ ] 분류 주제 5개 확정: 회의 · 할 일 · 일정 · 아이디어 · 미분류
- [ ] 정리 정책: 결과를 바로 적용하고, 되돌리기로 복구하며, 사용자가 직접 정한 분류는 다시 정리해도 유지한다
- [ ] 자동 보관 정책: 내용이 있는 탭은 자동으로 보관하고, Ctrl+S는 파일 저장으로 유지한다
- [ ] 성공 지표 수정: "정리 결과 긍정 평가율" 대신 "분류 정확도 80% 이상(정답 데이터 50개)"
- [ ] 기술 스택 명시: C# / .NET 10 / WinUI 3 (중간발표의 Python 표기를 수정)

### 단계 1. 자동화 빌드와 배포 (11/26 ~ 11/27) — 과제 필수

**목표:** push와 PR마다 자동으로 빌드와 테스트가 돌고, 태그를 붙이면 실행 파일 zip이 배포된다.

- `.github/workflows/ci.yml` (windows-latest)
  1. .NET 10 SDK 설치
  2. `dotnet run --project tests/MemoLite.Core.Tests` (Core 테스트)
  3. `dotnet build src/MemoLite -c Release -p:Platform=x64`
  4. `build.bat` 실행 → `artifacts/MemoLite`를 zip 아티팩트로 업로드
- `.github/workflows/release.yml`: `v*` 태그가 붙으면 zip을 GitHub Releases에 올린다 (과제 추가 항목 "배포")
- UI 스모크 테스트(`--smoke-test`)를 CI 러너에서 돌릴 수 있는지 확인한다. 안 되면 로컬 `Verify.ps1` 실행 로그를 결과물로 남긴다.
- `.gitattributes` 추가: 줄바꿈 CRLF/LF 혼용 경고를 없앤다.

**완료 기준:** Actions 탭에 성공한 빌드 로그가 있고, README에 빌드 배지가 있다.

### 단계 2. Core 모듈 분리와 데이터 모델 v2 (11/27 ~ 11/29) — N-006

**목표:** 이후 단계가 서로 충돌하지 않도록 관리, 정리, 검색 코드를 먼저 나눈다.

```
src/MemoLite.Core/
  Memos/MemoRecord.cs      메모 데이터
  Memos/MemoStore.cs       관리: 추가·수정·휴지통·복원, memos.json 원자적 저장, 창 간 잠금
  Organizing/Classifier.cs 정리: 주제 규칙, 신호 점수, 근거
  Organizing/Organizer.cs  정리: 정리 실행 기록과 되돌리기
  Organizing/LearnedRules.cs 정리: 개인 키워드 (단계 6)
  Searching/SearchService.cs 검색: 일치, 순위, 미리보기, 필터
```

**MemoRecord v2**

| 필드 | 설명 |
| --- | --- |
| `Id`, `Title`, `Body` | 메모 |
| `Category`, `CategorySource` | 주제와 출처: `None`(미정리) / `Auto` / `Manual` |
| `Reason` | 분류 근거 단어 목록 |
| `CreatedUtc`, `UpdatedUtc`, `OrganizedUtc` | 만든 시각, 고친 시각, 정리된 시각 |
| `DeletedUtc` | 휴지통에 넣은 시각 (없으면 활성) |
| `SourcePath` | 연결된 `.txt` 파일 (선택) |

- **마이그레이션:** 기존 `library.json`(v1)을 읽어 v2로 바꾼다. 주제가 `할 일`, `일정`, `아이디어`이면 그대로 두고 나머지는 `미분류`로 바꾼 뒤 `OrganizedUtc`를 비워서 다음 정리 대상이 되게 한다. 원본 v1 파일은 `library.v1.bak.json`으로 남긴다.
- 기존 `MemoLibrary.cs`의 원자적 저장, 잠금, 손상 파일 보호 로직은 `MemoStore`로 옮긴다.
- 지금 있는 Core 테스트 54개는 새 구조로 옮기고 모두 통과해야 한다.

**완료 기준:** 화면 동작은 그대로이고, 테스트가 통과하며, 모듈별 파일이 분리되어 있다.

### 단계 3. 자동 보관과 메모 목록 (11/29 ~ 12/02) — F-001 ~ F-004

**목표:** 쓰기만 하면 목록에 나타난다. 이수진이 저장을 몰라도 메모를 잃지 않는다.

- **자동 보관:** 세션 자동 저장(750ms) 타이머에서 내용이 있는 탭을 `MemoStore`에 반영한다. 새 탭은 처음 글자를 입력할 때 메모 레코드가 생긴다.
- **제목 없는 메모의 닫기:** 보관함에 있으므로 저장 확인 없이 닫는다. 메모는 목록에 남는다.
- **파일 탭:** 지금처럼 Ctrl+S로 파일에 저장하고, 파일에 저장하지 않은 변경은 ●로 표시한다. 보관함에도 자동으로 반영된다.
- **삭제 (F-003):** 사이드바 우클릭 또는 `Delete` 키를 누르면 휴지통으로 이동하고, 열린 탭도 닫는다. 휴지통에서 복원하거나 영구 삭제한다. 영구 삭제는 확인 대화상자를 띄운다.
- **사이드바 목록 (F-004):** 전체 / 미분류 / 주제별 / 휴지통. 항목에는 제목, 미리보기 한 줄, 날짜를 보여 준다. 누르면 탭으로 열린다.
- **새 메모 버튼:** 사이드바 맨 위에 둔다 (저니맵 "빠른 새 메모 진입").

**완료 기준 (PRD 수용 기준)**
- F-001: 새 메모에 글을 쓰면 1초 안에 목록에 나타난다.
- F-002: 고친 내용은 앱을 껐다 켜도 유지된다.
- F-003: 삭제한 메모는 목록에서 사라지고 휴지통에서 복원할 수 있다.
- F-004: 목록에서 메모를 누르면 전체 내용이 열린다.
- UI 스모크 테스트에 위 네 가지 시나리오를 추가한다.

### 단계 4. 정리 개편 (12/02 ~ 12/05) — F-005 ~ F-007

**목표:** 버튼 한 번으로 정리하고, 결과를 이해하고, 틀리면 바로 고친다.

**분류 규칙 (`Classifier`)**

| 주제 | 키워드 신호 | 구조 신호 |
| --- | --- | --- |
| 회의 | 회의, 회의록, 안건, 참석, 논의, 결정, 미팅, 보고 | 줄 머리 `참석:`, `안건:`, `결정:` |
| 할 일 | 해야, 요청, 지시, 마감, 제출, 확인 부탁, 처리, 할 일, todo | `[ ]`, `[x]`, `☐`, 줄 끝 `~하기`, `~까지` |
| 일정 | 일정, 약속, 예약, 출장, 방문 | 날짜(`11/25`, `11월 25일`), 시각(`오후 3시`, `15:00`), 요일, `D-3` |
| 아이디어 | 아이디어, 구상, 제안, 개선, 아이템 | `~하면 어떨까`, `~해 보면` |
| 미분류 | 아래 기준을 넘지 못했을 때 | |

- 제목의 신호는 본문의 2배로 계산한다.
- **미분류 기준:** 1등 점수가 최소 점수보다 낮거나 2등과 점수 차이가 작으면 미분류로 둔다. 기준 값은 단계 7의 정답 데이터로 정한다.
- 결과에는 근거 단어를 최대 3개까지 저장한다.

**정리 버튼 (`Organizer`)**
1. 대상: `CategorySource`가 `Manual`이 아니고, 아직 정리하지 않았거나 정리 뒤에 고친 메모
2. 결과를 바로 적용하고, 이번 실행의 이전 값을 기억한다 (되돌리기용)
3. 사이드바 맨 위에 배너를 띄운다: `8개 정리됨 · 회의 3 · 할 일 2 · 미분류 1  [되돌리기]`
4. 이번에 분류된 메모에 "새로 분류" 표시를 단다 (다음 정리 전까지)

**분류 칩 (F-007):** 편집기 메뉴줄 오른쪽에 `● 회의 · '안건', '참석'  ▾`. 누르면 주제를 고르는 메뉴가 열린다. 고르면 `Manual`이 된다. 사이드바 우클릭 메뉴의 `분류 변경 ▸`도 같은 동작이다.

**완료 기준**
- F-005: 정리 버튼을 누르면 대상 메모가 분류되고 배너가 나타난다.
- F-006: 목록에서 각 메모의 주제가 보인다.
- F-007: 메모를 열면 원문과 분류, 근거가 함께 보인다.
- 되돌리기를 누르면 정리 전 상태로 돌아간다 (테스트).
- 직접 정한 분류는 다시 정리해도 바뀌지 않는다 (테스트).

### 단계 5. 검색 개선 (12/05 ~ 12/07) — F-008, N-002

**목표:** 입력 한 번으로 찾고, 키보드만으로 연다.

- 범위: 휴지통을 뺀 모든 메모 (열린 탭도 보관함 메모이므로 따로 나누지 않는다)
- 사이드바에서 주제를 고른 상태라면 그 안에서만 찾는다. 검색창의 `#회의 예산`도 같은 동작이다.
- 결과 항목: 제목, 주제 배지, 날짜, **검색어가 굵게 강조된** 미리보기 한 줄
- 조작: ↑↓ 이동, Enter 열기, Esc 닫기. 메모를 열면 첫 일치 위치를 선택한다.
- 순위: 제목 일치 → 본문 일치 횟수 → 최근 수정

**완료 기준**
- F-008: 검색어가 들어간 메모가 결과에 보인다 (테스트).
- N-002: 메모 500개 검색이 1초 이내이다. 성능 테스트가 500개와 5,000개 결과를 로그로 남긴다.

### 단계 6. 적응형 학습 (12/07 ~ 12/09) — 창의성, Adaptiveness

**목표:** 사용자가 분류를 고칠수록 다음 정리가 그 사람에게 맞아진다.

- 분류를 직접 바꾸면 그 메모 **제목의 단어**를 새 주제의 개인 키워드로 저장한다 (`rules.json`).
  - 단어 처리: 띄어쓰기와 문장부호로 나누고, 끝의 흔한 조사(은/는/이/가/을/를/에/에서/의/로/으로)를 뗀다. 한 글자 단어와 숫자는 뺀다.
  - 같은 단어가 같은 주제로 2번 이상 옮겨지면 가중치를 올린다. 다른 주제로 옮겨지면 낮춘다.
- 개인 키워드로 분류되면 칩에 `내 규칙: '주간보고'`라고 근거를 보여 준다.
- 사이드바 메뉴 `학습된 규칙 보기`에서 목록을 보고 지울 수 있다. 별도의 설정 화면은 만들지 않는다.

**완료 기준:** "주간보고" 제목 메모 2개를 회의로 옮긴 뒤 새 "주간보고" 메모를 정리하면 회의로 분류된다 (테스트).

### 단계 7. 측정, 테스트 로그, 발표 준비 (12/09 ~ 12/13)

- **분류 정확도:** 직장인 업무 메모 50개 이상에 정답 주제를 붙인 `tests/data/labeled-memos.json`을 만들고, 정확도와 주제별 혼동표를 출력하는 테스트를 만든다. 목표는 80% 이상이다. 미분류 기준 값도 이 데이터로 조정한다.
- **실행 시간 (N-001):** 창이 뜨고 입력할 수 있을 때까지의 시간을 첫 실행과 재실행으로 나눠 잰다. 0.5초를 넘으면 PRD 수치를 실제 값에 맞춰 고친다.
- **사용자 테스트 (N-003, 성공 지표):** 3~5명을 대상으로 한다. 과제는 메모 10개를 정리하고 특정 메모 찾기 3건이다. 수동 정리와 MemoLite 정리에 걸린 시간을 비교하고, 과제 성공률을 잰다.
- **결과물:** CI 빌드 로그, 테스트 로그(Core, UI 스모크, 정확도, 성능), 기능 화면 캡처, 데모 영상(저니맵 순서: 수집 → 정리 → 탐색 → 활용).

## 5. 범위에서 뺀 것

경량 프로그램이라는 목표를 지키기 위해 아래는 만들지 않는다.

- 협업, 동기화, 알림, 위젯 (PRD 범위 밖)
- 외부 AI/LLM 분류 (PRD 제약)
- 사용자 정의 주제, 규칙 편집 화면 (학습 규칙 보기와 삭제만 제공)
- 사용 기록 수집 (성공 지표는 사용자 테스트로 측정)
- 초성 검색, 다음 일치로 이동(F3) — 시간이 남으면 추가
